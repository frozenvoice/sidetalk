# 전용 환경 준비와 설정 복구

시작 메뉴에서 **SIDETALK**를 엽니다([설치·업데이트·제거](INSTALL.md)). 소스 checkout에서는 `build-local.cmd`가 설치본을 만들고 갱신합니다. 공식 카카오톡과 Sandboxie Plus 1.18.4의 설치는 사용자가 별도로 진행해야 합니다.

## 앱에서 한 번 승인

앱은 실제 적용 INI 경로, 일반 사용자 컨텍스트의 기존 프로필과 저장소, 전용 box의 소유 표식, 전체 명시적 설정과 상속 규칙, 설치 구성요소의 서명·버전을 확인합니다. 정책 검사에서 중단된 진단의 빈 PID 배열을 전용 box가 비었다는 증거로 사용하지 않습니다. 복구 계획은 프로세스를 별도로 조회합니다.

준비가 필요하면 화면의 **복구하고 실행 준비**에서 변경 내용과 차단 이유를 확인합니다. 자동 복구 동의를 선택하면 이후 동일한 사용자·프로필·설치·실제 설정 경로와 검토 기준 안에서 같은 문제만 다시 처리합니다. 동의는 앱에서 해제할 수 있습니다. 복구 동의는 카카오톡 실행이나 로그인 동의가 아닙니다.

승인 가능한 변경은 다음으로 제한합니다.

- 새 사용자는 기존 프로필·SIDETALK box·중단된 프로필 흔적이 없을 때만 전용 프로필과 `IsolationPolicy.Expected`의 전용 섹션을 준비합니다. 기존 프로필이나 소유 식별자를 새로 만들어 문제를 숨기지 않습니다.
- `WindowsRasMan`, `OnScreenKeyboard`, `WindowsLive`, `Edge_Fix`, `OfficeLicensing`, `OfficeClickToRun` 중 실제 남아 있는 전역 Template 선택만 제거합니다. 이름뿐 아니라 공식 v1.18.4 원문의 출처·내용·값 순서와 실제 상속 결과를 함께 확인합니다.
- 서비스가 반환한 **현재 사용자 섹션**의 `SbieCtrl_AutoRunSoftCompat`만 `n`으로 설정합니다. 사용자 섹션 식별자를 하드코딩하거나 기존 사용자 설정 전체를 교체하지 않습니다.
- 오래된 호환성 선택을 다시 쓸 수 있는 열린 관리 UI가 있으면 승인 화면에 대상을 명시합니다. 공식 설치 경로·서명·버전, PID·생성 시각, 현재 사용자·세션을 확인한 관리 UI만 종료 대상으로 취급합니다. 이름만 보고 종료하지 않으며 카카오톡·Start.exe·서비스·드라이버를 복구 목적으로 종료하지 않습니다.

앱은 전체 INI와 변경 계획을 먼저 백업하고 재발 방지, 필요한 설정 변경, 파일/API 재검사를 수행합니다. **실행 준비**가 되면 **보조 카카오톡 실행**을 누르고 기존 실행 확인을 거쳐 공식 창에서 보조 계정으로 로그인합니다. 이미 정상인 환경에는 설정을 다시 쓰거나 불필요한 백업을 만들지 않습니다.

## 안전하게 처리할 수 없는 상태

실행 판단은 지원 호스트·일반 사용자 컨텍스트, 공식 설치·검토 버전, 현재 격리 정책과 상속 규칙, 전용 소유 정보·실제 저장 경로, 새 프로세스 조회와 미완료 명령·실제 설정 변경 기록으로 결정합니다. 이 검사에 실패하면 실행과 종료를 차단합니다.

재발 방지 옵션 `SbieCtrl_AutoRunSoftCompat=n` 미설정과 자동 복구 미동의는 실행 차단 조건이 아닙니다. 현재 정책이 정상이면 실행할 수 있고, 옵션은 최초 승인으로 적용할 수 있는 준비 상태로 표시됩니다. 실제 전역 Template이 정책과 충돌하면 기존 정책 차단과 승인 복구가 필요합니다.

전역 변경의 영향을 받는 다른 box, 변조된 공식 기준, 다른 사용자·세션의 관리 UI, 신원을 조회할 수 없는 관리 프로세스는 공유 INI 복구를 차단합니다. 일반 실행은 별도 검사 결과로 판단합니다. 공유 설정을 변경할 때는 다른 세션을 무시하지 않으며 다른 사용자의 프로세스는 종료하지 않습니다. `UserSettings_*`는 사용자 UI 설정이며 다른 box로 세지 않습니다. 영향 대상과 이유는 앱에 표시됩니다.

프로필·계정·대화·파일·레지스트리·명령 기록은 삭제하지 않습니다. 실패 후에는 복구 내역과 백업 위치를 확인하고 앱에서 상태를 다시 확인합니다. 부분 완료나 중단 기록을 자동 삭제하거나 성공으로 처리하지 않습니다. 다른 프로세스가 바꾼 설정을 전체 백업으로 덮어쓰는 롤백도 하지 않습니다.

권한·설정 암호·검토되지 않은 다른 box 구성 문제를 해결하려고 관리자 실행이나 전역 허용 목록 확대를 요구하지 않습니다. 해당 상태는 자동 복구 범위 밖으로 남습니다.

## 프로그램 호환성 창이 다시 나타나는 이유

SbieCtrl 자동 호환성 창의 **확인과 X는 모두 선택된 템플릿을 적용**합니다. ‘이후 소프트웨어 호환성을 확인하지 않음’만 체크해도 현재 선택 적용은 취소되지 않습니다. 목록에서 거절하면 `TemplateReject`가 저장되므로 복구 우회 방법으로 사용하지 않습니다.

`SbieCtrl_AutoRunSoftCompat`는 SbieCtrl의 사용자별 UI 자동 검사 옵션이며 보안 격리 옵션이 아닙니다. SbieCtrl은 시작 시 이 값을 읽고 이미 열린 창에는 오래된 상태가 남을 수 있어, 복구는 관리 UI 상태 확인을 포함합니다. SandMan은 별도의 Qt 설정 경로를 사용하므로 이 옵션을 SandMan 설정으로 간주하지 않습니다. 정확한 소스는 [공식 근거](SOURCES.md#sbiectrl-자동-호환성-창)에 있습니다.

어떤 카카오톡 업데이트나 run-local.cmd가 템플릿을 추가했다고 판단하지 않습니다. 자동 복구도 매번 실제 현재 상태와 승인 범위를 다시 확인합니다.

## 진단과 보존

앱의 복구 내역 버튼에서 백업과 단계별 기록 위치를 확인할 수 있습니다. 전체 INI 백업에는 로컬 설정 값이 있으므로 공유 전에 검토하세요. 진단·화면에는 인증정보·대화 내용·소유 토큰을 출력하지 않습니다.

`--diagnose`와 모든 `--render` 모드는 설정 쓰기·자동 복구·카카오톡 실행 없이 조회만 합니다. 진단 파일과 렌더링 이미지 외에 복구 기록이나 동의를 생성하지 않습니다. Codex/MSIX에서 실행한 결과는 탐색기에서 연 일반 사용자 GUI의 성공을 대신하지 않습니다.

전용 INI 내보내기는 검토용 기능으로 유지합니다. 일상적인 초기 준비에 터미널, RESTORE 입력, INI 직접 편집은 필요하지 않습니다.

## 중단된 준비를 앱에서 재조정

1. 시작 메뉴의 **SIDETALK**를 열고 **초기 설정 · 진단**을 엽니다.
2. 중단 파일의 분류와 차단 이유를 확인한 뒤 **원본을 보존하고 다시 확인**을 누릅니다. 이 조작은 일반 설정 복구 계획이 차단돼 있어도 자체 안전 조건이 충족되면 사용할 수 있습니다.
3. 보존 후 새 복구 계획을 확인합니다. 승인된 작업과 일치하는 근거만 기존 중단 재조정 흐름으로 연결하며, 필요한 경우 **복구하고 실행 준비**에서 새로 확인한 내용을 승인합니다.
4. 정상 재조회로 **실행 준비**가 된 뒤 보조 카카오톡을 실행합니다. 진단 저장과 보존 내역 확인은 원인 확인에 사용할 수 있습니다.

완전한 승인 이벤트, 같은 최초 프로필 후보, 잘린 파일, 기존 파일과의 충돌, 출처 불명을 구분합니다. 모든 `.tmp`를 일괄 삭제하거나 무조건 무시하지 않습니다. 동의 저장 실패는 자동 처리 권한을 주지 않지만 현재 정상 정책의 실행을 막는 실제 설정 변경으로 취급하지도 않습니다.

보존은 명령 잠금 다음 복구 잠금 순서로 진행하며 미완료 명령·진행 작업과 파일·설정 변경을 다시 확인합니다. 원본 바이트·SHA-256·원래 위치·보존 위치·관련 작업을 덮어쓰지 않는 기록으로 남깁니다. 위치는 `%LOCALAPPDATA%\SIDETALK\recovery-evidence`이며 `setup-recovery`의 임시 파일 탐지 범위 밖입니다. 보존 기록도 개별 해시와 구조를 검증합니다. 링크와 경로 이탈은 차단합니다. 보존 중 다시 중단돼도 원본·보존본·대응 기록을 확인하고 이어갑니다.

파일 보존은 작업 완료가 아닙니다. 실제 INI/API·프로필·명령 상태를 재검사합니다. 출처가 불명확하거나 기존 정상 파일과 충돌하면 보존 후에도 이유를 표시하고 필요한 조작을 계속 차단합니다. 승인된 최초 프로필 후보는 같은 BoxName·OwnerToken·저장 경로를 유지하며 다른 프로필을 덮어쓰지 않습니다.
## 생성 규칙

- `Enabled=y`: 명시적 전용 box 실행.
- `FileRootPath`: 사용자별 SIDETALK 저장소의 고유 하위 폴더.
- `BoxInfo`: 로컬 프로필과 일치하는 SIDETALK 소유 표식. Sandboxie의 보안 기능으로 오인하지 마세요.
- `WriteFilePath`: 현재 사용자 프로필, 실제 Roaming/Local AppData 경로, ProgramData의 Kakao 폴더를 호스트에서 숨기고 보조 환경에서 새로 작성하도록 요청.
- `WriteKeyPath`: HKCU 및 HKLM의 Kakao 키에 같은 분리 규칙 적용.
- `AutoDelete=n`, `NeverDelete=y`: 자동 삭제 금지.
- `AutoRecover=n`: 보조 환경 파일의 호스트 자동 복구 금지.
- `DropAdminRights=y`: 관리자 권한을 내리고 Sandboxie의 일반 보안 격리를 사용. 유료 강화 모드나 보안 격리를 해제하는 App Compartment 모드는 사용하지 않음.
- `ForceProcess`, `ForceFolder`, 호스트 직접 접근, 임의 실행 트리거, 탈출 규칙, 사용자 DLL 주입 없음.

**이 파일은 실행 호환성 인증서가 아닙니다.** 공식 규칙의 의미와 현재 엔진 구현을 근거로 작성한 후보 설정이며, 실제 보조 프로필의 분리·영속성은 설치 후 실측해야 합니다.

## 실행 중 상태와 종료

이전 화면의 우상단 **정책 미확인** 표시는 현재 INI가 검증되지 않았다는 뜻과 다릅니다. 현재 화면은 **현재 격리 설정 확인됨 · 시작 당시 적용 규칙은 확인 불가**를 따로 표시합니다. SIDETALK는 현재 전용 box 설정과 전역 규칙을 확인할 수 있지만, 이미 실행된 프로세스가 시작될 때 Sandboxie에서 어떤 규칙을 적용받았는지는 API로 소급 증명할 수 없습니다. 이 상태만으로 로그인·인증·송수신 성공을 판정하지도 않습니다.

평소에는 보조 카카오톡의 자체 트레이 메뉴로 정상 종료합니다. 종료 후 SIDETALK에서 **상태 새로 확인**을 눌러 전용 box가 비었고 현재 격리 설정이 확인됐는지 확인한 뒤 다음 실행을 준비합니다. 새로 실행한 프로세스도 시작 당시 적용 규칙은 확인 불가로 표시됩니다. 트레이 종료 뒤에도 프로세스가 남고 **보조 카카오톡 강제 종료** 버튼이 활성화된 경우에만 누르세요. 이 버튼은 SIDETALK가 소유한 전용 환경 전체에 `/terminate`를 보내는 강제 종료라서 보조 카카오톡과 그 환경의 보조 프로세스를 모두 끝내며, 미저장 작업이 손실될 수 있습니다. 실행·종료가 차단된 상태에서는 버튼도 비활성화되므로, 진단에 표시된 설정 차단 사유를 확인하고 설정을 복구한 뒤 새로고침합니다. 저장된 보조 환경 파일과 레지스트리를 자동 삭제하지는 않습니다.

## 차단 사유별 대응

| 표시 | 대응 |
|---|---|
| 미설치/서명 오류 | 공식 설치 출처·경로 확인. 자동 다운로드/무서명 허용 없음 |
| 버전 검토 필요 | 현재 설치를 보존하고 해당 버전의 API·규칙을 검토. 자동 업/다운그레이드 없음 |
| 소유 정보 불일치 | 기존 profile.json/INI 백업을 비교. 새 소유 표식을 임의로 붙여 기존 box를 인수하지 않음 |
| 전역/템플릿 설정 검토 필요 | 차단 항목과 진단을 수집해 정책 검토. 다른 box를 위해 쓰는 전역 규칙은 바꾸지 않음 |
| 경로 불일치/연결 경로 | Junction/symlink/리다이렉션을 우회하지 않음. 기존 데이터 이동 없음 |
| API 실패/서비스 미응답 | 설치 프로그램/서비스 상태를 사용자가 확인. SIDETALK는 서비스 시작·재시작이나 드라이버 설정을 변경하지 않음 |
| 실행 응답 불명 | 프로세스 상태를 다시 확인. 중복 실행/광역 종료 없음 |

업데이트 후에는 호스트와 샌드박스에 서로 다른 카카오톡 실행 파일이 있을 수 있습니다. 기존 파일을 지우지 말고 진단 버전과 실제 보조 앱의 도움말 버전을 비교해 재검증합니다.

## 0.1.1 정책 2

공식 기본 템플릿에 포함된 호스트 WebCache COM/IPC 연결은 전용 환경의 ClosedClsid 및 ClosedIpcPath 규칙으로 차단합니다. 기존 사용자 파일·레지스트리 숨김과 자동 삭제 금지도 계속 필요합니다. BreakoutDocument 등의 호스트 실행 패턴을 추가하면 검사를 통과하지 못합니다.

0.1.0의 정책 1 INI를 이미 내보냈다면 0.1.1에서 다시 내보내세요. 같은 프로필·박스·저장 경로를 유지합니다. 적용 전에 새 파일을 검토하고, **승인한 SIDETALK 전용 섹션만** 갱신해야 합니다. 0.1.5의 승인된 복구 범위 밖에 있는 기존 정책 업그레이드는 자동 적용하지 않습니다. 저장 데이터는 삭제하지 않습니다. 아직 적용 전이면 새 파일을 사용하면 됩니다.

## 상태 조회 오류 안내 — 0.1.6

`복구 상태 확인 실패`는 복구 계획 조회 단계의 오류다. 같은 주기에 실행 검사가 성공했다면 그 새 결과로 실행·종료 권한을 판단하고 복구만 차단한다. 실행 조회 자체의 실패나 실제 설정 변경의 결과 불명 상태에서는 실행·종료 권한을 해제한다. 이전 정보를 `마지막 확인`으로 표시하는 경우 이전 CanLaunch/CanStop 값은 재사용하지 않는다. `상태 새로 확인`으로 재시도하고 계속 실패하면 앱의 진단 저장 기능을 사용한다. 이 오류를 해결하려고 전역 Template을 지우거나 profile.json을 새로 만들지 않는다.

진단은 오류 단계와 예외 체인·스택을 포함한다. UI 오류 기록은 `%LOCALAPPDATA%\SIDETALK\diagnostics`에 가능한 경우 저장하며, 기록 실패가 앱의 상태 표시를 방해하지 않는다. 공유 전에는 진단의 나머지 로컬 경로도 확인한다.
