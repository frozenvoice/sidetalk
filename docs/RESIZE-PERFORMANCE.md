# 메인 창 리사이즈 성능 — 2026-10-25

## 증상과 확인된 원인

창 가장자리·모서리를 끌어 크기를 바꾸면 창이 마우스를 늦게 따라오고 화면이 끊겼다. 측정 결과 원인은 SIDETALK의 레이아웃이나 4초 자동 확인이 아니라 **하드웨어 렌더링 WPF 창의 크기 변경 경로**였다. 크기가 바뀔 때마다 UI 스레드가 GPU 렌더 대상의 재구성·표시를 기다린다. 측정 PC(Windows 11 10.0.26300, 4K 59 Hz, 배율 100%, AMD 내장 GPU + NVIDIA RTX 5080, WPF 렌더 티어 2)에서는 SIDETALK 콘텐츠가 없는 **빈 WPF 창**도 같은 현상을 보였다.

`SetWindowPos`를 125 Hz로 연속 호출한 측정(3초, 375단계)의 결과는 다음과 같다.

| 조건 | 크기 메시지 처리 p50 | SetWindowPos p95 | 렌더 프레임 | 최대 프레임 간격 |
|---|---|---|---|---|
| 빈 WPF 창 (하드웨어) | 0.41 ms | 102 ms | 25/s | 278 ms |
| 탭 콘텐츠 숨김 | 0.81 ms | 106 ms | 24/s | 197 ms |
| 보조 카카오톡 탭 | 3.15 ms | 152 ms | 25/s | 273 ms |
| 초기 설정 · 진단 탭 | 8.88 ms | 186 ms | 16/s | 382 ms |
| 보조 카카오톡 탭, 이 창만 소프트웨어 | 3.51 ms | 9 ms | 123/s | 29 ms |
| 초기 설정 · 진단 탭, 이 창만 소프트웨어 | 9.49 ms | 16 ms | 115/s | 31 ms |

- WPF가 크기 메시지 안에서 동기로 수행하는 레이아웃은 탭에 따라 p50 4~13 ms로 한 프레임 예산 안이었다(진단 탭과 펼친 Expander, 실행 · 식별 탭이 가장 큼).
- 16 ms를 넘는 Dispatcher 작업은 모든 시나리오에서 0건이었다. 4초 자동 확인(합성 컨트롤러와 실제 읽기 전용 컨트롤러 모두)과 고대비 팔레트는 결과를 바꾸지 않았다. 따라서 자동 확인 주기·상태 갱신 로직은 변경하지 않았다.

## 수정

`src/Sidetalk.App/InteractiveResizeRendering.cs`가 **사용자가 크기를 조절하는 동안에만** 이 창의 렌더 모드를 소프트웨어로 바꾸고, 크기 조절이 끝나면 이전 모드로 되돌린다.

- 시작: 복원 상태 창의 크기 조절 테두리를 누를 때(`WM_NCLBUTTONDOWN`의 HTLEFT~HTBOTTOMRIGHT) 또는 `WM_SIZING`(키보드 크기 조절 포함).
- 종료: `WM_EXITSIZEMOVE`. 크기 조절 루프 없이 버튼을 놓으면 `WM_NCLBUTTONUP`.
- 창 이동, 최대화·복원, 스냅은 하드웨어 경로를 유지한다. 최대화 상태의 테두리 클릭은 전환하지 않는다.
- 사용자나 시스템이 이미 소프트웨어 렌더링을 지정한 창·프로세스는 건드리지 않는다.
- 메시지는 관찰만 한다. Windows의 크기 조절 루프, WPF 레이아웃, 최소 크기, 다크·고대비 테마, 접근성은 그대로다. 상태 확인·실행·종료·복구 로직은 바뀌지 않았다.

## 수정 전후 비교 (실제 Windows 크기 조절 루프)

`SendInput`으로 오른쪽 아래 테두리를 누르고 125 Hz로 4초 동안 끈 결과(같은 실행, 같은 창; "수정 전"은 진단용으로 후크를 뗀 상태). 지연은 다음 이동 직전 포인터 목표 대비 창 크기 차이다.

| 시나리오 | 처리된 WM_SIZING | 렌더 프레임 | 프레임 간격 p95 | 지연 p50 / p95 | 놓은 뒤 도달 |
|---|---|---|---|---|---|
| 보조 카카오톡 탭, 수정 전 | 40 | 25.6/s | 118.6 ms | 39 / 125 px | 67 ms |
| 보조 카카오톡 탭, 수정 후 | 371 | 149.5/s | 16.0 ms | 0 / 9 px | 0 ms |
| 초기 설정 · 진단 탭, 수정 전 | 41 | 21.9/s | 189.0 ms | 38 / 110 px | 49 ms |
| 초기 설정 · 진단 탭, 수정 후 | 253 | 102.8/s | 16.9 ms | 2 / 10 px | 9 ms |
| 실행 · 식별 탭, 수정 후 | 231 | 87.7/s | 17.1 ms | 3 / 13 px | 0 ms |
| Sandboxie 설치 안내 + 4초 자동 확인, 수정 후 (9초) | 652 | 117.6/s | 15.5 ms | 1 / 10 px | 3 ms |
| 주입한 고대비 팔레트, 수정 후 | 378 | 151.3/s | 15.9 ms | 0 / 9 px | 0 ms |

모든 수정 후 시나리오에서 드래그 종료 뒤 원래 렌더 모드로 돌아왔다. 렌더 모드 전환은 드래그마다 한 번 약 95~105 ms의 프레임 간격을 만든다. 크기 조절 중 UI 스레드의 크기 메시지 처리는 탭에 따라 p50 9~17 ms이며, 이는 남은 레이아웃 비용이다.

## 재현

```powershell
# 프로그램 구동 리사이즈 + 원인 분리(빈 창, 콘텐츠 숨김, 창 단위 소프트웨어 비교)
$env:SIDETALK_RESIZE_PROBE_ONLY = 'isolate'
dotnet run --project tests/Sidetalk.UiChecks -c Release -- <출력 폴더> --resize-probe
# 실제 크기 조절 루프로 수정 전후 비교 (약 1분 동안 마우스 커서가 자동으로 움직이고 원위치로 돌아감)
$env:SIDETALK_RESIZE_PROBE_ONLY = 'drag'
dotnet run --project tests/Sidetalk.UiChecks -c Release -- <출력 폴더> --resize-probe
# 탭·Expander·자동 확인·고대비·실제 읽기 전용 컨트롤러 시나리오 (환경 변수 없이)
dotnet run --project tests/Sidetalk.UiChecks -c Release -- <출력 폴더> --resize-probe
# 사람이 직접 40초 동안 크기를 조절하며 기록
dotnet run --project tests/Sidetalk.UiChecks -c Release -- <출력 폴더> --resize-interactive
```

프로브는 합성 컨트롤러(또는 `--diagnose`와 같은 읽기 전용 컨트롤러)를 사용하며 실행·종료·복구·설정 쓰기를 하지 않는다. 타이밍은 PC마다 다르므로 `verify.ps1`에는 넣지 않았다. 대신 `verify.ps1 -UiChecks`의 `ResizeRenderingChecks`가 전환 조건과 복원, 이동·최대화 시 비전환을 결정적으로 검사한다. 이번 측정 JSON과 로그는 `artifacts/verification/resize-perf`에 있다.

## 검증하지 못한 범위

- Windows 디스플레이 배율 125%·150%: 사용자 설정을 바꾸지 않기 위해 측정하지 않았다(측정 PC는 100%).
- 실제 Windows 고대비 설정: 주입한 팔레트로만 측정했다.
- 사람이 직접 마우스로 끈 체감: Computer Use 도구를 사용할 수 없어 `SendInput` 합성 드래그로 대체했다.
- 다른 GPU 구성(단일 GPU, 내장 GPU만, 원격 데스크톱): 측정하지 않았다. 원인이 하이브리드 GPU 환경에서 특히 크게 나타나는지는 확인하지 못했다.
